# Darts Leaderboard — дизайн приложения

Дата: 2026-08-17

## Цель

Заменить Excel-таблицу, в которой сейчас вручную ведётся счёт при игре в дартс, веб-приложением: те же привычные столбцы игроков и строки раундов, но со автоматическим подсчётом остатков, живой статистикой, графиком трендов и хранением результатов в базе.

Приложение домашнее, работает в локальной сети, авторизации нет: любой, кто открыл страницу, может всё.

## Технологический стек

- .NET 8, C#
- Blazor Server (режим интерактивности InteractiveServer)
- MudBlazor последней актуальной версии
- PostgreSQL 16, доступ через EF Core 8
- xUnit для тестов, Testcontainers для интеграционных, bUnit для минимального покрытия UI
- Запуск в Docker через docker compose

## Архитектурные решения

| Решение | Выбор | Причина |
| --- | --- | --- |
| Модель хостинга | Blazor Server | UI вызывает Application-слой напрямую, без HTTP API и дублирования DTO |
| Стиль Application-слоя | Явные use case-сервисы в DI, без MediatR и CQRS-инфраструктуры | Логики мало, сквозных задач почти нет, косвенность не окупается |
| Полнота хранения | В БД пишутся все броски, а не только итоги | Объём данных ничтожен, любая аналитика доступна задним числом |
| Состояние идущего матча | Write-through: каждый бросок сразу в БД, состояние восстанавливается из истории | Матч переживает перезагрузку страницы, обрыв соединения и рестарт контейнера; несколько устройств видят одно и то же |
| Правила игры | Приложение не сторожит правила дартса, только считает очки | Перебор, недобор и закрытие даблом игроки определяют сами у мишени |
| Запуск | Docker Compose (приложение + Postgres) | Домашний сервер поднимается одной командой |

## Структура решения

Пять проектов в `DartsLeaderboard.sln`, зависимости направлены строго внутрь:

- `DartsLeaderboard.Domain` — сущности, правила режимов игры, расчёт статистики. Без внешних зависимостей, включая EF Core.
- `DartsLeaderboard.Application` — use case-сервисы, интерфейсы репозиториев, DTO для UI. Знает только Domain.
- `DartsLeaderboard.Infrastructure` — `DbContext`, конфигурации сущностей, реализации репозиториев, миграции. Знает Application и Domain.
- `DartsLeaderboard.Web` — Blazor Server с MudBlazor, страницы и компоненты, точка сборки DI. Ссылается на Application, а на Infrastructure — только в `Program.cs` для регистрации служб.
- Тесты: `DartsLeaderboard.Domain.Tests`, `DartsLeaderboard.Application.Tests`, `DartsLeaderboard.Infrastructure.Tests`, `DartsLeaderboard.Web.Tests`.

UI не ссылается на Domain: страницы работают с DTO из Application. Маппинг стоит немного лишнего кода, зато граница реальная, а модель отображения меняется без правок домена.

## Доменная модель

### Сущности

- `Player` — игрок справочника: идентификатор, имя, признак архивности, дата создания. Архивный игрок не предлагается при наборе участников, но его матчи и победы сохраняются.
- `Match` — агрегат: режим игры и его настройки, участники, упорядоченный список бросков, время старта и завершения, статус, победитель.
- `MatchParticipant` — участник матча: ссылка на игрока и порядок столбца в таблице.
- `Throw` — одна запись таблицы: номер раунда, участник, набранные очки. Один бросок в терминах приложения это три дротика, записанные одним числом.

### Правила режимов

Режимы вынесены в стратегию `IGameRules`, отвечающую на три вопроса: как бросок меняет состояние игрока, закончен ли матч, кто победил.

- `X01Rules` — начальный счёт настраивается (301, 501, 701 или произвольное значение), очки вычитаются из остатка. Остаток ровно ноль означает победу и немедленное завершение матча. Проверок на дабл и перебор нет.
- `HighestTotalRules` — фиксированное число раундов (по умолчанию 5, настраивается при старте), очки суммируются. После последнего раунда побеждает наибольшая сумма; при равенстве матч завершается без победителя (ничья).

### Инварианты агрегата

- Нельзя записать бросок в завершённый или прерванный матч.
- Броски идут по кругу в порядке участников; вне очереди записать нельзя.
- Отменить можно только последний записанный бросок.
- Очки броска в диапазоне 0..180. Пустое поле ввода трактуется как 0, то есть незачтённый раунд (перебор или недобор).
- В режиме x01 очки броска не могут превышать текущий остаток игрока: такой ввод отклоняется с подсказкой, что при переборе записывается 0. Это единственная проверка, связанная с правилами; она нужна, чтобы остаток не уходил в минус.
- Матч завершается автоматически, как только правило режима сообщает об этом; отдельной операции «завершить» нет.
- В матче не меньше двух участников; состав участников после старта не меняется.

### Статистика

Статистика — вычисляемая проекция агрегата, а не хранимые поля. По каждому игроку: максимум, минимум, среднее, сумма и текущий остаток (для x01). По матчу: лучший и худший бросок с автором, средний раунд, число сыгранных раундов.

Нули учитываются как полноценные броски во всех показателях, поскольку означают сыгранный, но незачтённый раунд. Следствие: у игрока, словившего перебор, минимум и худший бросок равны нулю, а среднее просаживается — это осознанное поведение, отражающее реальную игру.

Пересчёт идёт по списку бросков в памяти при каждом вводе, поэтому живая статистика во время матча и статистика восстановленного из БД матча считаются одним и тем же кодом.

## Application-слой

Каждая операция — отдельный сервис с одним публичным методом, регистрируется как scoped. Ожидаемые ошибки возвращаются как результат с кодом, а не исключением.

Справочник игроков:

- получить список игроков (с фильтром по архивности)
- добавить игрока
- переименовать игрока
- отправить игрока в архив и вернуть из архива

Матч:

- начать матч: режим, настройки режима, выбранные участники в заданном порядке
- записать бросок текущему игроку
- отменить последний бросок
- получить состояние матча
- прервать матч без результата (статус «отменён», в лидерборд не попадает)

Чтение:

- лидерборд: игрок, число побед, число сыгранных матчей, доля побед
- история завершённых матчей
- список незавершённых матчей для продолжения

### Поток записи броска

1. Загрузить агрегат матча из БД вместе с участниками и историей бросков.
2. Восстановить состояние проигрыванием бросков через правила режима.
3. Применить новый бросок, проверив инварианты.
4. В одной транзакции сохранить новый бросок и, если матч закончился, статус, время завершения и победителя.
5. Разослать уведомление об изменении матча и вернуть UI свежий DTO состояния.

Тот же путь загрузки и восстановления используется при открытии страницы матча, поэтому перезагрузка вкладки, обрыв соединения Blazor Server и рестарт контейнера состояние не теряют.

### Одновременная работа с двух устройств

Уникальность броска по тройке «матч, участник, номер раунда» обеспечивается индексом в БД. При одновременной записи одного раунда с двух устройств вторая операция падает на конфликте уникальности, use case возвращает код ошибки «раунд уже записан», UI показывает сообщение и перечитывает состояние. Молчаливого удвоения очков произойти не может.

### DTO для UI

- `MatchStateDto` — участники как столбцы, раунды как строки, очки и остатки по ячейкам, личная статистика, статистика матча, серии для графика, чей ход, статус матча и победитель.
- `PlayerDto` — игрок справочника.
- `LeaderboardRowDto` — строка лидерборда.

## Схема БД

PostgreSQL, имена таблиц и столбцов в snake_case, идентификаторы целочисленные с автоинкрементом (номер матча показывается пользователю).

- `players` — имя с уникальным индексом без учёта регистра, признак архивности, дата создания.
- `matches` — режим, настройки режима (начальный счёт либо число раундов), время старта, время завершения, статус (идёт, завершён, отменён), победитель.
- `match_participants` — матч, игрок, порядок столбца; уникальность игрока внутри матча и уникальность порядка внутри матча.
- `throws` — матч, участник, номер раунда, очки, время записи; уникальный индекс по матчу, участнику и номеру раунда.

Лидерборд считается SQL-запросом по матчам и участникам, без денормализованных счётчиков: домашние объёмы этого не требуют, а рассинхронизации по построению не будет.

Миграции применяются при старте приложения с повтором до готовности Postgres, чтобы `docker compose up` на чистом volume поднимался с первого раза.

## Интерфейс

Оболочка — MudBlazor с тёмной темой: `MudAppBar` и `MudDrawer` с разделами «Матчи», «Игроки», «Лидерборд», «История».

### Экраны

- **Главная (лидерборд)** — таблица игроков с победами, числом матчей и долей побед; кнопка «Новый матч»; список незавершённых матчей для продолжения.
- **Игроки** — справочник: добавление, переименование, архивирование.
- **Новый матч** — выбор режима переключателем, настройка режима рядом (начальный счёт 301/501/701 или произвольный; число раундов для режима на максимум, по умолчанию 5), выбор игроков чекбоксами с управлением порядком столбцов, кнопка «Начать».
- **Матч** — компоновка варианта C из макета: шапка с режимом, номером матча, текущим раундом и активным игроком; слева таблица, справа панель статистики матча, под таблицей график трендов.
- **История** — список завершённых матчей (режим, участники, победитель, дата); по клику открывается экран матча в режиме только для чтения.

Макеты вариантов компоновки лежат в `.mockups/layout.html`; принят вариант C.

### Таблица матча

Столбец — участник, строка — раунд, как в исходном Excel. В ячейке крупно очки раунда, мелко остаток (для x01). Подвал таблицы показывает остаток, максимум с минимумом и среднее по каждому игроку.

Ввод: числовое поле сфокусировано в ячейке активного игрока, Enter записывает бросок и передаёт ход следующему, пустое значение означает ноль, диапазон 0..180. Кнопка отмены откатывает последний бросок. Кнопки крупные, рассчитаны на ввод пальцем с планшета.

### График трендов

`MudChart` в виде линий: по горизонтали номер раунда, по каждому игроку своя линия. Переключатель метрики: очки за раунд (виден разброс) и накопительная сумма (видно, кто вырывается вперёд). В режиме на максимум график раскрыт всегда, в режиме x01 свёрнут по умолчанию.

### Живое обновление

После успешной записи броска приложение публикует уведомление через notifier в памяти; открытые страницы этого матча по событию перечитывают состояние. Одного инстанса приложения для дома достаточно, внешний брокер не нужен.

### Ошибки

Ожидаемые ошибки (нельзя записать в завершённый матч, раунд уже записан, очки вне диапазона, некорректный состав участников) возвращаются use case-ами как результат с кодом и показываются через `MudSnackbar`. При конфликте одновременной записи UI перечитывает состояние матча и просит повторить ввод.

## Тестирование

Основной вес — на домене. xUnit со штатными `Assert`, без FluentAssertions (несвободная лицензия новых версий).

- `Domain.Tests` — списание очков и победа при точном нуле в x01; суммирование, завершение после последнего раунда и ничья в режиме на максимум; ноль как незачтённый раунд и его влияние на среднее; отмена последнего броска; порядок передачи хода; запрет записи в завершённый матч; расчёт статистики, включая матч без бросков.
- `Application.Tests` — use case-ы на фейковых репозиториях в памяти: восстановление состояния из истории, автоматическая финализация, отмена броска, прерывание матча, коды ошибок.
- `Infrastructure.Tests` — Postgres в контейнере через Testcontainers: применение миграций на чистой базе, срабатывание уникального индекса броска, загрузка агрегата с историей, запрос лидерборда.
- `Web.Tests` — пара тестов bUnit на компонент таблицы: пустое значение даёт ноль, Enter записывает бросок и передаёт ход. Остальной UI проверяется руками.

## Docker и конфигурация

- Многоступенчатый `Dockerfile`: сборка на образе SDK 8, запуск на `aspnet:8.0-alpine` под непривилегированным пользователем.
- `docker-compose.yml`: сервис приложения на порту 8080 и `postgres:16-alpine` с именованным volume и healthcheck, от которого зависит старт приложения.
- Строка подключения и пароль задаются переменными окружения; в репозитории лежит `.env.example`.
- README: запуск в две команды и адрес для захода с телефона в домашней сети.
- Git-репозиторий инициализируется в рамках проекта; `.gitignore` покрывает `bin`, `obj`, `.env`, `.superpowers`, но не `.mockups`.

## Вне области видимости

Осознанно не делаем в этой итерации:

- Авторизация, учётные записи, разграничение доступа.
- Графики и тренды по истории матчей: только внутри идущего матча.
- Проверка правил дартса приложением (дабл-аут, автоматическое определение перебора).
- Ввод отдельных дротиков вместо суммы за раунд.
- Режимы игры помимо x01 и «максимум за N раундов»; Cricket, легы и сеты.
- Экспорт данных, PWA и офлайн-режим, мобильное приложение.
